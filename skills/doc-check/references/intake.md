# 11. New client files (tmp/)

Section 11 of the doc-check skill, split out of SKILL.md; read when the table in SKILL.md section 1 says so. "Sections 1–9" are SKILL.md sections; section 10 is in `references/crm-recording.md`, 12 in `references/filing.md`, 13 in `references/old-folder.md`: read them together with this file, in one turn (SKILL.md section 1); one not yet in the conversation: read it at the step below that names it, in the same turn as that step's other calls.

When the user asks, in any language, to process, handle, work on or check a deal or its documents ("process the Whitmore deal", "what's new for Whitmore?", "check Whitmore's documents", "process the new files in the tmp of deal Whitmore"), whether any client has sent new documents or files ("any new documents from clients?"), or to process new files without naming a deal ("process the new client files"). New files sit as-is in `<deal folder>/tmp/`, not yet named or filed. Needs the CRM (SKILL.md section 1); without the CRM: check the files in `tmp/` like files in the client folder (sections 1–9), do not register, do not file. Each turn handles only ONE deal.

**The deal's `tmp/` is the source of truth for new files**, whatever brought them there: the client portal, email (`mail-intake` or the organisation's shared mailbox), a staff upload in the app, or files someone dropped into the OneDrive folder. Never answer "no new files" from the portal's intake items or from `deal_files_list` alone; only from a listing of `tmp/` (below).

Where to look:
- **Backend listing of `tmp/` (main source).** `genation-workspace_deal_intakes_list` whose items have `source`: the backend lists every file in `<deal folder>/tmp/` on the organisation's OneDrive (through Microsoft Graph), so it works before OneDrive on this computer has synced, and without it. Item: `dealId`, `dealTitle`, `contactName` (portal uploads only), `source` (`portal` uploaded by the client on the portal, `tmp` any other file in `tmp/`), `fileName`, `path`, `driveItemId`, `uploadedAt`, `status`, `dealFileId`, `checkStatus`. `status` is `new` until the file is registered on the deal (10.1), then becomes `processed` automatically with `dealFileId`; `processed` only means registered, not yet checked or filed. `checkStatus` is the check status of the file on the deal (`null` while still `new`). Filter `status` = `unchecked`: items registered but never checked (an earlier run, a staff upload), still waiting for check and filing. Read all pages by `cursor`.
- **Local listing (fallback).** `guroos_customer_files` of the deal folder, only when there is no backend listing: no `deal_intakes_list` tool, or it reports `module_not_enabled` or `503` (the organisation's OneDrive is not connected); its items have no `source` (an older backend that lists only portal uploads): use both, the local listing for the rest of `tmp/`.
- **Files on the deal still in `tmp/`** (`deal_files_list`, `document.path` inside `/<deal folder>/tmp/`): not checked (`latestCheck` empty) go into the batch; already checked: filing only (section 12).
- **No duplicates.** A file is only one item: same `driveItemId` (file on the deal: `document.driveItemId`) or same path (item: `path`; file on the deal: `document.path`; file in the vault: `/<deal folder>/tmp/<file name>`; case-insensitive) means the same file.

**Reading.** Every file is read on this computer with `guroos_document_read` (`customer` = deal folder, `file` = `tmp/<file name>`). The answer "There is no file", or "No folder matches" for the deal folder: OneDrive on this computer has not synced it yet; do not ask the user for a name, do not search for it. Such a file is still registered (by `itemId`), but not checked or filed this time; the summary names it as waiting for OneDrive (step 6). "The document vault is not connected on this computer": register every new item all the same, check nothing, say so once.

**Turns** ("Fewer turns", SKILL.md section 1). A deal's run usually takes these turns, each with every call listed, in parallel; skip what does not apply; a step that must ask the user ends the turn:
1. `modules_list`, the reads of SKILL.md section 1, and `deals_list` (step 1) when the deal is not known yet;
2. with the deal: `deals_get`, both `deal_intakes_list` calls (step 2), `deal_files_list`; `guroos_customer_files` of the deal folder only for the local listing (fallback; `folderPath` of `deals_list` or `deals_get`; none: section 13 first);
3. every registration (step 3) and `guroos_document_read` of every batch file;
4. the rule files of the batch's types, the compact `document_types_list`, `required_documents_list`, and pages still needed;
5. every check (`guroos_date_check`, `guroos_identity_check`, `guroos_abn_lookup`, page images), with 10.3 for every file and the `codes` read;
6. 10.4 and 10.2 for every file;
7. 12.1 for every file still in `tmp/`;
8. the report, the summary and ONE `question` (asked to file: every `deal_files_file` first).

0. **No deal named** (the conversation has not named one either): with `deal_intakes_list`, call it twice, no deal filter: `status` = `new` (new files, not registered) and `status` = `unchecked` (registered, not checked). Group by `dealId`: deal name (`dealTitle`), number of new files, number of unchecked files, client name (`contactName`, when an item has one), latest upload date; the deal with the latest upload first. With `genation-workspace_deals_list`: call it ONE more time with `unassigned` = `true` (read all pages) to flag deals nobody has claimed; all three calls in ONE turn. List, then ask which deal to process, end the turn, even when there is only one deal (the deal may belong to another staff member) or the user asks to process all:

   ```
   New files in the deals' tmp/ folders, not yet processed:
   1. <deal name> · <n> new files · <m> files not checked · <client name> · latest <DD/MM/YYYY> · unassigned
   2. <deal name> · <n> new files · latest <DD/MM/YYYY>
   Which deal would you like to process?
   ```

   Drop any part whose count is 0 or that has no value. No items: "No new or unchecked files in the deals' tmp/ folders." Items without `source` (an older backend: portal uploads only): heading "Files clients sent through the client portal, not yet processed:", no items "No new or unchecked files from clients through the client portal.", and in both cases one more line: files sent by email or copied into `tmp/` are not in this list; ask to "process deal <name>" to see that deal's `tmp/`. No `deal_intakes_list`: ask the user which deal, stop. Do not scan the vault for `tmp/` yourself.
1. **Deal:** the deal the user chose at step 0 (that group's `dealId`), the deal being discussed in the conversation, or `genation-workspace_deals_list` (`search` = the name the user gave, deals not archived). Exactly ONE deal: use it. Several deals: list the names (`title`) and ask, stop. None: say so and ask, stop. The user names or chooses several deals: ask which deal first, stop. Call `genation-workspace_deals_get` to get the deal's clients (Applicant, section 2), folder and owner, in the turn of step 2's lists. `ownerId` empty: nobody has claimed the deal (usually a deal the client created on the portal); still process it, mention it in the summary (step 6), do not claim the deal yourself. Only when the user asks to claim it ("claim this deal"): `genation-workspace_deals_update` with `id` and `claim` = `true`; error `deal_already_owned`: say someone else has already claimed the deal.
2. **Files in `tmp/`:**
   - With `deal_intakes_list`: call it with `dealId`, once `status` = `new` (not registered) and once `status` = `unchecked` (registered, not checked). `unchecked` items are already on the deal: do not register them again, go straight to classify and check (steps 3, 4).
   - Deal folder = `folderPath`. No `folderPath`, or `folderReplaceable` true: do section 13 first (the client's old folder: read `references/old-folder.md`); attached: deal folder = the `folderPath` just attached; no candidate or staff do not attach: `folderPath`, else `plannedFolderPath`; both empty: say the deal has no folder yet, stop. Drop the leading `/`: that path is the `customer` of every `guroos_…` call (never search it with `guroos_customers`). Local listing (fallback only): `guroos_customer_files` (`customer` = that path).
   - New or unchecked items, files on the deal in `tmp/`, or files in the local `tmp/` (fallback): continue, even when OneDrive on this computer does not have the files yet.
   - None of these: say "no new files in `<deal folder>/tmp/`" only after the backend listing (or, without it, the local listing) found none. Deal without `folderPath`, or with `folderReplaceable` true: section 13 has already searched, do not search again: say it, stop. Deal already has `folderPath`: find candidate folders with `guroos_customers` (`query` = deal name, a name, never a path: top-level folders) and `guroos_customer_files` on the parent of the deal folder (usually `Customers`: deal folders with the same client name); files sent before the deal had a folder may sit in another folder (`…_PUR OO` instead of `…_PUR OO_WBC`, because `plannedFolderPath` changes with loan purpose, OO/INV and lender). Leave out every folder that is another deal's folder (equal to, inside or containing the `folderPath` of a deal returned by `genation-workspace_deals_list` with `includeArchived` = `true`, all pages, once with `contactId` = each client's `contactId` and once with `search` = each client's family name; case-insensitive, without the leading `/`): its `tmp/` files belong to that deal. List the remaining folders with files in `tmp/` whose name contains the deal's client name (with file count), say that files are only registered and filed when they are in `<deal folder>/tmp/`: staff move the files there, then ask again. Stop: do not choose yourself, do not register files in another folder, do not move or rename anything. No candidate: say "no new files in `<deal folder>/tmp/`", stop.
3. **Register and batch:** follow 10.1 (`references/crm-recording.md`, section 10):
   - `deal_files_list` (read all pages) once, in the turn of `deals_get`;
   - then in ONE turn: register each `new` item by `itemId`, whether or not this computer has the file yet (`unchecked` items are not registered again); fallback only: each file in the local `tmp/` that matches no file on the deal and no item, by `path`; an item that could not be registered whose file is in the local `tmp/`: by `path` in the next turn. Files just registered: use the registration results; list the deal's files again only after a `409` (10.1).

   Batch = files in `tmp/` just registered or already on the deal but not checked (`latestCheck` empty: a staff upload, an earlier run), plus the files of every `unchecked` item (the file on the deal with `id` = `dealFileId`); the user asks for a re-check: every document file in `tmp/`. Files in `tmp/` already checked: do not check again, only plan filing (section 12). Read every batch file as in "Reading" (`file` = `document.path` relative to the deal folder, `tmp/<file name>`), in the turn of the registrations (reading does not wait for them). A file this computer does not have yet: registered, not checked, not filed; the next time the user asks, it is still in the batch because `latestCheck` is still empty.
4. **Each file:** read and check per sections 3–8 (not section 9: CRM present), each step for every file at once. Then do section 10 in this order:
   - 10.3 (type, client) for every file in the batch, and the rules of the types in the batch, read ONCE with `codes` ("Document types and rules", start of section 10): in the turn of the checks, once the types and clients are known;
   - then, in ONE turn, for every file: 10.4 (required document), 10.2 (result with `ruleResults`).
5. **Filing** per section 12 (`references/filing.md`), for every file of the deal still in `tmp/`, all plans (12.1) in ONE turn: file only when the user asked to ("process and file"), otherwise propose it (approval rule, SKILL.md section 1).
6. **Summary** after the report (section 7), one block for the whole `tmp/`:

```
### New files · <deal name> · <deal folder>/tmp/
Deal has no owner: click "Claim deal" in the app, or ask the assistant to "claim this deal".
Just attached the client's old folder to the deal: <deal folder>.
- <file name> · <client sent via portal: <client name>, <DD/MM/YYYY> | in tmp/, <DD/MM/YYYY>>
  - On the deal: <just registered | already there | not registered: reason>
  - Type · client: <type label> · <client name> | not classified: <reason>
  - Required document: <name> (<just linked | already linked>) | none | not linked: <reason>
  - Check: <Conclusion> · <satisfied | needs attention | incomplete | not checked> (<met count>/<rule count> criteria) | not checked: <reason>
  - Filing: <awaiting approval (no. n below) | filed in <subfolder>/<new name> | already in place | left in tmp/: <reason>>
Files in tmp/ still new: <file name> (<reason>), … | none left
Files in tmp/ still not checked: <file name> (<reason>), … | none left
Waiting for OneDrive on this computer: <file name>, …
```

- The "Deal has no owner" line only when the deal's `ownerId` is empty. The "Just attached the client's old folder" line only when this turn attached a folder per section 13. The two lines "still new", "still not checked" only with `deal_intakes_list`: items registered (including `409`) have become `processed`; items not registered stay `new`, with the reason; items registered but whose check result could not be recorded (10.2) stay `unchecked`, with the reason. Write the block from what steps 1–5 returned (`checkStatus` of the 12.1 plan); do not call `deal_intakes_list` or `deal_files_list` again for it.
- Each new or unchecked item gets one `- <file name>` entry (`fileName`), even when not registered; `source` `portal`: "client sent via portal"; other files: "in tmp/" (`uploadedAt`, or the date in the listing).
- Files not checked because OneDrive on this computer has not synced them: "not checked: waiting for OneDrive on this computer", the "Waiting for OneDrive" line names them (otherwise leave that line out), then add the line "Ask again to "process new files for deal <deal name>" in a few minutes to check the remaining files."

Check status by the file's `checkStatus`: `satisfied` satisfied, `needs_attention` needs attention, `incomplete` incomplete (criteria not yet met), `unchecked` not checked. Non-document file: one line `- <file name> · not a document, left in tmp/`. After the block: the filing list of section 12.3 (if any), then the next steps of SKILL.md section 7, everything staff need to decide in ONE `question` call (filing, open check items of 12.5, the questions of 10.3, 10.4), per the approval rule (SKILL.md section 1).
