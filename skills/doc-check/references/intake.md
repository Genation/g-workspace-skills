# 11. New client files (tmp/)

Section 11 of the doc-check skill, split out of SKILL.md; read when the table in SKILL.md section 1 says so. "Sections 1–9" are SKILL.md sections; section 10 is in `references/crm-recording.md`, 12 in `references/filing.md`, 13 in `references/old-folder.md`: read them together with this file, in one turn (SKILL.md section 1); one not yet in the conversation: read it at the step below that names it, in the same turn as that step's other calls.

When the user asks, in any language, to process, handle, work on or check a deal or its documents ("process the Whitmore deal", "what's new for Whitmore?", "check Whitmore's documents", "process the new files in the tmp of deal Whitmore"), whether any client has sent new documents or files ("any new documents from clients?"), or to process new files without naming a deal ("process the new client files"). New files sit as-is in `<deal folder>/tmp/`, not yet named or filed. Needs the CRM (SKILL.md section 1); without the CRM: check the files in `tmp/` like files in the client folder (sections 1–9), do not register, do not file. Each turn handles only ONE deal.

**The deal's `tmp/` is the source of truth for new files**, whatever brought them there: the client portal, email (`mail-intake` or the organisation's shared mailbox), a staff upload in the app, or files someone dropped into the OneDrive folder. Never answer "no new files" from the portal's intake items (`deal_intakes_list`) or from `deal_files_list` alone; only from a listing of `tmp/` (below).

Where to look:
- **Backend listing of `tmp/` (main source).** `genation-workspace_deal_tmp_files_list` reads the files directly in `<deal folder>/tmp/` from the organisation's OneDrive (Microsoft 365), so it sees a file as soon as it is on OneDrive, before OneDrive on this computer has synced it, and without it. Query: `dealId` (one deal, read live; without it, the open deals of the organisation), `status` = `new` or `registered` (without it, both). Item: `dealId`, `dealTitle`, `name`, `path`, `driveItemId`, `createdAt`, `modifiedAt`, `status`, `dealFileId`, `intakeId`. `new`: no file on the deal shows it yet, to register (10.1). `registered`: on the deal (`dealFileId`), not filed yet, still in `tmp/`: checked or not, per `deal_files_list`. `intakeId` set: a client sent it through the portal. Result: `items` (no pages, at most 200), `dealsUnread` (deals whose `tmp/` could not be read: `folder_not_found` the deal folder is gone from OneDrive or moved, `unavailable` OneDrive failed, try again later), `truncated` (more deals or files than one call reads).
- **Local listing (fallback).** No `deal_tmp_files_list` tool (an older backend), or it reports `503` (OneDrive not connected) or this deal in `dealsUnread`: do as before: `genation-workspace_deal_intakes_list` (portal uploads; read all pages by `cursor`) with `status` = `new` (not registered) and `status` = `unchecked` (registered, never checked), plus `guroos_customer_files` of the deal folder for the rest of `tmp/`. An intake item: `dealId`, `dealTitle`, `contactName`, `fileName`, `path`, `driveItemId`, `uploadedAt`, `status`, `dealFileId`, `checkStatus`. No `deal_intakes_list` either (the `client_portal` module is not enabled), or it reports `module_not_enabled`: the local listing only.
- **Files on the deal still in `tmp/`** (`deal_files_list`, `document.path` inside `/<deal folder>/tmp/`; a staff upload is one at once): not checked (`latestCheck` empty) go into the batch; already checked: filing only (section 12).
- **No duplicates.** A file is only one item: same `driveItemId` (file on the deal: `document.driveItemId`) or same path (item: `path`; file on the deal: `document.path`; file in the vault: `/<deal folder>/tmp/<file name>`; case-insensitive) means the same file.

**Reading.** Every file is read with `guroos_document_read`: `customer` = deal folder, `file` = `tmp/<file name>` (the row's `path` relative to the deal folder), plus `cloud` = `{"dealId": …, "driveItemId": …}` from the listing row (a `deal_tmp_files_list` item, an intake item, or `dealId` and `document.driveItemId` of a file on the deal) whenever it has a `driveItemId`. The app reads the file on this computer when OneDrive has synced it, otherwise it downloads it from OneDrive through the server. OneDrive can take 5–8 minutes to bring a new deal folder to this computer: that never holds up the check; never tell the user to wait for OneDrive or to ask again later because of it. Still "There is no file" or "No folder matches" with `cloud` (an older app, or the file just left `tmp/`): "not checked: could not be read (<the tool's words>)"; do not ask the user for a name, do not search for it. A read refused as invalid or unprocessable ("the server refused it (unprocessable_entity)"…) usually means a mistyped `cloud` id, not an OneDrive failure: copy `dealId` and `driveItemId` again from the listing row and read that file again once, in the next turn, before reporting it (SKILL.md section 1 "Ids"); still refused: "not checked: could not be read (<the tool's words>)". A file with no `driveItemId` (only in the local `tmp/`): without `cloud`. "The document vault is not connected on this computer": register every new file all the same (without type or client), check nothing, say so once.

**Turns** ("Fewer calls and turns", SKILL.md section 1). A deal's run usually takes these turns, each with every call listed, in parallel; skip what does not apply; a step that must ask the user ends the turn:
1. the reads of SKILL.md section 1, and `deals_list` (step 1) when the deal is not known yet;
2. with the deal: `deals_get`, `deal_tmp_files_list` with `dealId` (step 2), `deal_files_list`; the local listing's calls only as its fallback (`folderPath` of `deals_list` or `deals_get`; none: section 13 first);
3. `guroos_document_read` of every batch file, the compact `document_types_list`, `required_documents_list`, and `deal_intakes_list` with `dealId` when a file has an `intakeId` (the item with its `driveItemId`: `contactId`, `contactName` = who sent it; fallback: already read);
4. the rule files of the batch's types and `cross-checks.md` (it also holds SKILL.md sections 5 and 7, the source file check and the report), and pages still needed, including what the cross-checks need from the same person's documents already on the deal (`cross-checks.md`, "Documents already on the deal": every set is recomputed from all of them each run, e.g. the period of each of the person's payslips whose name does not give it) and what the duplicate comparison needs (10.6: every file to register or file, also those checked earlier);
5. every check (`guroos_date_check`, `guroos_identity_check`, `guroos_abn_lookup`, page images), every registration with its type and client (step 3; not likely duplicates, 10.6), 10.3 for files already on the deal, the `codes` read, and with a payslip, rental, Centrelink, child support or loan or card statement, `fact_file_get` `summary` of the records (10.2, "Records"), and with a `proof_of_ownership` document whose type has a second folder, `securities_list` (12.1, "Category folder");
6. 10.4 and 10.2 for every file;
7. 12.1 for every file still in `tmp/` (not likely duplicates), with 10.5's retry or follow-up of refused findings;
8. `deal_files_file` for every file whose plan has no blockers (12.3);
9. one reply: the report, the summary, the lines after filing, then the review items (SKILL.md section 7), if any. Never review items without the report and summary above them.

Group by `dealId`: deal name (`dealTitle`), number of `new` files, number of `registered` files (on the deal, not filed yet), how many came through the client portal (`intakeId` set), latest `createdAt`; the deal with the latest file first. List, then ask which deal to process, end the turn, even when there is only one deal (the deal may belong to another staff member) or the user asks to process all:

   ```
   Which deal would you like to process?
   ```

No items: "No files waiting in the deals' tmp/ folders." No `deal_tmp_files_list`, or it reports `503`: `deal_intakes_list` twice, no deal filter (`status` = `new` and `unchecked`), grouped the same way with the client (`contactName`), heading "Files clients sent through the client portal, not yet processed:", no items "No new or unchecked files from clients through the client portal.", and in both cases one more line: files sent by email or copied into `tmp/` are not in this list; ask to "process deal <name>" to see that deal's `tmp/`. Neither tool: ask the user which deal, stop. Do not scan the vault for `tmp/` yourself.
1. **Deal:** the deal the user chose at step 0 (that group's `dealId`), the deal being discussed in the conversation, or the deal found from the names the user gave (SKILL.md section 1 "Finding the deal": through the clients, deals not archived). 2. **Files in `tmp/`:**
   - `deal_tmp_files_list` with `dealId`, without `status`. `new` files: register (step 3). `registered` files are already on the deal: do not register them again; the file in `deal_files_list` with `id` = `dealFileId` (or the same `driveItemId`) says whether it is checked (steps 3, 4); none there: the file was replaced or archived on the deal (staff replaced it in the app, or archived a duplicate, 10.6): `deal_files_get` it (`id` = `dealFileId`, in turn 3), then leave it: not in the batch, never read, checked or compared for duplicates (SKILL.md section 1 "Replaced files"), summary line `- <file name> · <replaced by <replacedByName> | archived> on the deal, left in tmp/`; the file that replaced it is checked and filed as usual. Fallback (Where to look): the two `deal_intakes_list` calls with `dealId`; `unchecked` items are already on the deal, go straight to classify and check.
   - Deal folder = `folderPath`. No `folderPath`, or `folderReplaceable` true: do section 13 first (the client's old folder: read `references/old-folder.md`); attached: deal folder = the `folderPath` just attached; no candidate or staff do not attach: `folderPath`, else `plannedFolderPath`; both empty: say the deal has no folder yet, stop. Drop the leading `/`: that path is the `customer` of every `guroos_…` call (never search it with `guroos_customers`). Local listing (fallback only): `guroos_customer_files` (`customer` = that path).
   - `new` or `registered` files, files on the deal in `tmp/`, or (fallback) intake items or files in the local `tmp/`: continue, even when OneDrive on this computer does not have the files yet ("Reading").
   - None of these: say "no new files in `<deal folder>/tmp/`" only after the backend listing (or, without it, the local listing) found none. The backend found none: list the local `tmp/` once (`guroos_customer_files`); files there that the backend does not list are still uploading to OneDrive: name them, say to ask again in a few minutes, stop. Deal already has `folderPath`: find candidate folders with `guroos_customers` (`query` = deal name, a name, never a path: top-level folders) and `guroos_customer_files` on the parent of the deal folder (usually `Customers`: deal folders with the same client name); files sent before the deal had a folder may sit in another folder (`…_PUR OO` instead of `…_PUR OO_WBC`, because `plannedFolderPath` changes with loan purpose, OO/INV and lender). Leave out every folder that is another deal's folder (equal to, inside or containing the `folderPath` of a deal returned by `genation-workspace_deals_list` with `includeArchived` = `true`, all pages, once with `contactId` = each client's `contactId` and once with `search` = each client's family name; case-insensitive, without the leading `/`): its `tmp/` files belong to that deal. List the remaining folders with files in `tmp/` whose name contains the deal's client name (with file count), say that files are only registered and filed when they are in `<deal folder>/tmp/`: staff move the files there, then ask again. Stop: do not choose yourself, do not register files in another folder, do not move or rename anything. No candidate: say "no new files in `<deal folder>/tmp/`", stop.

3. **Batch and register** (10.1, `references/crm-recording.md`; `deal_files_list`, all pages, once in the turn of `deals_get`):
   - Batch = the `new` files, plus the files in `tmp/` already on the deal but not checked (`latestCheck` empty: a staff upload, an earlier run; fallback: the files of `unchecked` items, `id` = `dealFileId`); the user asks for a re-check: every document file in `tmp/`.    - Read every batch file as in "Reading", in ONE turn: reading needs no registration.    - Register each `new` file by `itemId` = `driveItemId`, synced to this computer or not, in the turn of the checks, with 10.3's `documentTypeCode`, `subjectContactId` and `assignedContactIds` in the same call (10.1); a file that could not be read or classified: without them, same turn. `registered` files and `unchecked` items are not registered again. 4. **Each file:** read and check per sections 3–8 (not section 9: CRM present), each step for every file at once. Then section 10 in this order:

Summary: `Required document: <sender>'s <name> still open: <sender> sent <owner>'s <document>`.

- The "Deal has no owner" line only when the deal's `ownerId` is empty. The "Just attached the client's old folder" line only when this turn attached a folder per section 13. "Still not registered": `new` files (or intake items) whose registration failed or was declined, or not done ("check only"), with the reason; "still not checked": files that could not be read, or whose check result could not be recorded (10.2), with the reason. Write the block from what steps 1–5 returned (`checkStatus` of the 12.1 plan); do not call `deal_tmp_files_list`, `deal_intakes_list` or `deal_files_list` again for it.
- Each file in `tmp/` gets one `- <file name>` entry (`name`, or `fileName` of an intake item), even when not registered: "client sent via portal" when it has an `intakeId` (fallback: an intake item, with "<client name>"), otherwise "in tmp/"; the date is `createdAt` (`uploadedAt` of an intake item), in the user's local time zone (SKILL.md section 6), as are the dates of steps 0 and 2. "Request (draft)" only when the check made a request (10.2).
- `Check:` gives every file's outcome and its reason in a few words: the main Notices or Could not check item of its report block ("pay period not printed", "address differs from the deal's"), or "all criteria met". Result not recorded on the CRM (file not registered, call refused): `not recorded: <reason>` only, never `PASS` or a criteria count; the file goes under "still not checked".
- `Fact Find:` only for a file recorded in this run: the report fields whose findings made a proposed value (10.2), such as "licence number, expiry, state, name on licence", then the exact words "added to Updates to review for you to accept" (never only "proposed in Updates to review"), plus values not proposed and why (10.2, "Records"; 10.5); staff accept them in the deal's Updates to review, never you.

Check status by the file's `checkStatus`: `satisfied` satisfied, `needs_attention` needs attention, `incomplete` incomplete (criteria not yet met), `unchecked` not checked. Non-document file: one line `- <file name> · not a document, left in tmp/`. After the block, in the same reply: the lines after filing (12.4), then the next steps and ONE numbered list of review items (SKILL.md section 7): the notes for the client word for word (10.2, "Another client's document"), open check items (12.5), likely duplicates (10.6), filing names (12.4), the questions of 10.3, 10.4, files still not registered or recorded after the id retry (SKILL.md section 1 "Ids"), e.g. "5. tmp/licence.pdf: not registered, so not checked on the CRM or filed: "The contact is not on this deal". Reply retry, or leave it." The report and this block come first: never review items alone.
