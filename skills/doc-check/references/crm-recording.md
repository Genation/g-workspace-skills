# 10. Recording results on the CRM

Section 10 of the doc-check skill, split out of SKILL.md; read it when the table in SKILL.md section 1 says so. "Sections 1–9" are SKILL.md sections; section 11 is in `references/intake.md`, 12 in `references/filing.md`, 13 in `references/old-folder.md` (read together with this file when the task needs them, SKILL.md section 1; one not yet in the conversation: read it when that table says, the same way).

If the organisation has the CRM (SKILL.md section 1), each document's check result is recorded on the deal in the CRM: Fact Find values become proposed values on the client's record in the deal, with the document as evidence, for staff to accept in Updates to review (10.2); items to notify are shown to staff. Files in the deal folder's `tmp/` not yet on the deal are registered on the deal (10.1), documents are classified (10.3) and complete a required document only when they fully meet it (10.4). Do not save results to the client folder (section 9 is not done when there is a CRM). Only copy the report: do not re-read, do not change conclusions, do not record anything the report does not have. Never call `genation-workspace_observations_record` directly, nor edit or accept Fact Find values (`applicant_details_update`, `deal_profiles_update`, `backfill_decide`), nor the work-history tools (`genation-workspace_processing_*`, `documents_record`, `documents_update_status`): the CRM's check records are the history. The CRM tools are the `genation-workspace_…` tools; when talking to the user, refer to clients and deals by name, never read out ids. A tool reports `module_not_enabled`: no CRM, skip this section.

**Document types and rules.** `genation-workspace_document_types_list` is called in two ways:
- **Compact list.** Call without filters ONCE for the whole batch, when first needed. Each type has `code`, `label`, `categoryFolder`, `fileNamePattern` and `checkRuleCount` (number of rules), NOT the rules. Use this list to classify (10.3), choose the `documentTypeCode` of a `request` (10.2) and read `fileNamePattern` (12.1). A type having no `checkRules` here does not mean the type has no rules.
- **Check rules.** Once 10.3 has decided the types of the batch's documents (in the turn of its `deal_files_update` calls), call again ONCE with `codes` = the list of distinct type codes in the batch (codes already on documents and codes just set). Each type returned has `checkRules`. A type set after that call: call once more, only with the missing codes. No document in the batch has a type: do not call. Do not send `includeRules: true` without `codes` (the result is very large).

### 10.1 Finding the document on the deal

Find each file before checking; register a file not yet on the deal in the turn of the checks, once its type and client are known ("Registering with the classification" below). Each file needs `document.id` (the stored document, NOT the `id` of the file on the deal), `dealId` and the `id` of the file on the deal:
- **File just registered in this conversation** (skill `mail-intake`, result of `genation-workspace_deal_files_register_existing`): an attachment or a file in the client folder with exactly the registered name uses the `id`, `document.id` and `dealId` of that result.
- **Batch's deal already known** (the client folder is the deal's folder, section 2 or section 11): `genation-workspace_deal_files_list` (`dealId`, read all pages by `cursor`) once for the whole batch; the file on the deal whose `document.path` equals `/<client folder path>/<file path>` (case-insensitive; e.g. `/Customers/Lan Quach_PUR OO/tmp/Lan_DL.pdf`) is that file.
- **Other files in the client folder:** `genation-workspace_documents_search` with `search` = file name (without folder); pick the item whose `path` matches as above. That item has exactly one `dealFiles`: use its `dealId`; several deals and one is the conversation's deal: that deal; otherwise: do not record, gather into the question at the end of the report "file <file> is on several deals: <deal names>, which deal should the result be recorded on?".
- **A file the backend lists in the deal's `tmp/`** (a `new` file of `deal_tmp_files_list`, section 11, whatever its source: portal, email, dropped into OneDrive; or, in its fallback, a `new` item of `deal_intakes_list`): register with `genation-workspace_deal_files_register_existing` with `dealId`, `itemId` = the item's `driveItemId`, not `path` (the file is already on the organisation's OneDrive, synced to this computer or not), and the classification ("Registering with the classification" below). Results as in the line below, except `404`: the file is no longer on the organisation's OneDrive (deleted or moved out), "not registered: file no longer on OneDrive", do not retry.
- **Already on the deal** (a `registered` file of `deal_tmp_files_list`, or an `unchecked` item of `deal_intakes_list`, section 11): do not register it again; use the file in `deal_files_list` whose `id` = the item's `dealFileId`.
- **File in the local `tmp/` of the deal folder that is not yet on the deal and has no item** (section 11's local listing, the fallback when there is no `deal_tmp_files_list` or it cannot read the deal's `tmp/`): register with `genation-workspace_deal_files_register_existing` with `dealId`, `path` = `/<deal folder>/tmp/<file name>`, relative to the organisation's root folder, and the classification ("Registering with the classification" below). Register only document files (PDF, image, DOCX, XLSX, CSV) directly in `tmp/` of the right deal folder; do not register files in other folders. Results:
  - Success: use the result's `id`, `document.id`. Deal has no folder yet (`folderPath` empty), or `folderReplaceable` is true: the first registration attaches `plannedFolderPath`, or makes the CRM's folder the deal's for good, after which an old folder can no longer be attached; so do section 13 (`references/old-folder.md`) before the first registration.
  - `404` (OneDrive has not finished syncing, or the file was just moved): register again once after the other files; still failing: "not registered: OneDrive has not finished syncing".
  - `409` (already on the deal): re-read `deal_files_list` to get that file. `503` (Microsoft 365 not connected or failing): do not register the remaining files, state the reason once. Other errors: copy the tool's message verbatim, do not retry.
- Not found (an attachment not registered in the conversation, a file outside `tmp/` not on any deal): that file is not recorded, reason "file not on the deal yet".

**Registering with the classification.** `genation-workspace_deal_files_register_existing` takes 10.3's fields in the same call: `documentTypeCode`, `subjectContactId`, and `assignedContactIds` (the document's client, plus the clients named jointly). Pass each one 10.3 has decided; omit the ones it has not (file not read, type not recognised, client unclear: those go to the final question). A file registered this way needs no `deal_files_update` or `deal_files_assign`. `422` for an unknown field (an older server, usually `assignedContactIds`): register again once without the fields it names, then set them with 10.3's `deal_files_update` / `deal_files_assign` in the next turn. Never pass `name`, `labels`, `requiredDocumentId` (10.4 links later), nor `replacesDealFileId` (only per 10.6). A likely duplicate (10.6) is not registered until staff decide.

Keep with each file: the document's `documentTypeCode` and `subjectContactId`, and the deal file's `assignedContactIds`, `latestCheck`, `checkStatus`, `filingState` (in the results above). If the deal is known before checking, get the Applicant as in section 2.

### 10.2 Recording each document

Call `genation-workspace_document_checks_record` ONCE for each document with a `Conclusion:` line ("Outside the checklist" lines and likely duplicates, 10.6, are not recorded; a file with several `(part n)` blocks is not recorded, reason "file has several documents"), every document in ONE turn, after the 10.3 updates have returned:

| Field | Value |
|---|---|
| `documentId` | `document.id` from 10.1 |
| `dealId` | the deal from 10.1 |
| `kind` | `deep` (full check against the checklist) |
| `outcome` | `PASS` → `verified`; `ACTION NEEDED`, `NOT ENOUGH INFORMATION` → `need_review`; `INVALID`, `UNREADABLE` → `not_met` |
| `model` | the running model ID when the system provides it; if not sure, omit |
| `findings` | per the table below, at most 200 items |
| `ruleResults` | the result of each rule of the document type, per "Per-rule results" below; only when the document already has a `documentTypeCode` |

**Findings (`findings`)**, one `kind` per item:

| Report | Finding |
|---|---|
| A "Record in Fact Find" line whose target is in the target table below | `{kind: "fact_find", target, value, message, ruleCode, contactId?, location?}` |
| Rule 2: Finance Clause / Loan Approval Date, Settlement Date | `{kind: "deal_date", target, value, message, ruleCode}` (do not add `fact_find` for these two lines) |
| A "Notices" `[TFN]` line | `{kind: "redact", message: <evidence: page with the TFN>, location?}`; never record the TFN number |
| Any other "Notices" line | `{kind: "notify", message: "[<tag>] <evidence> → <action>", request?}` |
| A "Could not check" line | `{kind: "notify", message: "Could not check: <item>: <what is missing>"}` |
| A "Record in Broker's Notes" line (rule 11) | `{kind: "broker_note", message: <that line>}` |

- **`fact_find` / `deal_date`:** `message` = the report line verbatim (`<Field>: <value>`, including period, tag, ABN lookup result). `value` = the value only, in the field's format: date `YYYY-MM-DD` (from DD/MM/YYYY); money as a decimal number without `$` or commas (`"1250.00"`; a loss with a leading minus, `"-12500.00"`); interest rate as a percentage number (`"6.14"`); ABN as 11 digits, ACN as 9 digits, with no spaces; text as printed. Do not send when the value is not one clear value: "not on the document", "not applicable", "none …", "Could not check", month/year only, a masked number (`…4821`), several values (split loan, several benefits), or `INVALID` / `UNREADABLE`. `asset.rental_income` is monthly rent: send only when the document prints it per month (per month, calendar month); do not convert periods yourself.
- **`contactId`:** omit it: the CRM uses the document's client (`subjectContactId`, set in 10.3). Send it only when a finding is about a different client of the deal than the document's (`company.*`, `entity_individual.*` on a document whose client is a person: the client that is the entity), copied character for character from `contacts` of `deals_get`. Do not pass `entityId`.
- **`location`:** the page if the report states it (`page 2`); otherwise omit.
- **`request`** (only with `notify`): only when the "action" is requesting a specific document from the client (a current copy, a full-period copy, a signed or certified copy, Statutory Declaration…): `{name: <document to request, brief>, documentTypeCode?, assignedContactIds, clientNote?}`. `documentTypeCode` only when exactly one type in the compact list of `genation-workspace_document_types_list` fits; `assignedContactIds` = `[<the document's client>]` (`subjectContactId`, 10.3; unknown: omit), so only that client is asked; `clientNote` per "What the client sees" below. The CRM creates a `draft` required document on the deal whose staff-only `comment` is the finding; staff decide whether to send it to the client.
- **Back** of a two-file block `<front> + <back>`: record the same `outcome` but omit the `fact_find` items (already recorded on the front).
- **Sensitive numbers:** only the targets below may receive the full number as in the Fact Find line (Licence No., passport Document No., loan Account number). Never send a TFN, card number, Medicare number, date of birth, CRN, MRZ line.
- **Where the values go.** Each `fact_find` finding on a target the CRM holds becomes a proposed value, with the document as evidence, on the client's record in the deal (rules 4–8: the client's applicant details in the deal: licence number, expiry and name; passport number, expiry and name; Medicare name and expiry; visa subclass, type and name); a `deal_date` likewise on the deal's loan requirement. Staff accept or reject each in the deal's Updates to review; until then `fact_file_get` still lists the field as missing, with `pendingCount`. These findings are the only way to record them, in both modes, covered by the batch's approval (SKILL.md section 1); never accept them yourself, never write them another way (see the start of section 10). Proposed: one per `observationIds` item of the result; a finding named in `warnings` made none, e.g. targets the CRM only stores (`company.acn`, `income.salary_sacrifice`, `business_income.profit_before_tax`, `asset.balance_sheet`, `other_adviser.conveyancer`, `entity_individual.*`). Say so per file (10.5; section 11's summary): "added to Updates to review for you to accept".

**What the client sees (`clientNote`).** The client portal shows a required document to a client only once staff send it (`requested`; or `rejected`, with staff's rejection note), only when it is assigned to that client or to no one, and only its `name` and `clientNote`. The `comment`, the check's findings and the report are staff only: never tell staff that the client will see something that is not in a `clientNote`.
- **Every `request` gets a `clientNote`** written to that client: what to send and, when it helps, why, in one or two short sentences of plain Australian English, e.g. "Please upload a payslip dated within the last 30 days." Only about that client's own document. Never internal findings (tags, conclusions, criteria, "edited", source file, figures or names that differ), tool or field names, ABNs, ID or account numbers, other people's names or details, or lender names, unless staff wrote them for the client. At most 1,000 characters.
- **Exact words first.** Show each note as `<client first name> will see, once you send the request: "<clientNote>"`. Ask first: write a note only after staff saw its exact words in a `question`. The batch's approval still to ask after the report (SKILL.md section 7): put the notes in that question; on approval send them as `request.clientNote` here. Changes approved before the notes were known (section 11 step 2, a clear instruction earlier in the chat): record each `request` without `clientNote`, put every note word for word in the question after the report ("Add this note to the draft request <name>? Daniel will see, once you send the request: "…"": "Add the note", "Change…", "No"), and on approval call `genation-workspace_required_documents_update` with `id` = that request's required document and `clientNote`, every note in ONE turn. Full access: send `request.clientNote` here, and quote each note in the report the same way.
- **Request's required document:** `requiredDocumentIds` of the result, in the order of the `request`s sent; a request named in `warnings` made none.
- **Older server:** the tool's `request` has no `clientNote` field, or the tool rejects it: record without it, then set it with `required_documents_update` as above (Full access: in the next turn). That tool has no `clientNote` either, rejects it, or returns the required document without the note: say "<client> will not see a reason for <request> on the client portal; tell them directly", once per request.

**Per-rule results (`ruleResults`).** A document type's check rules are the type's `checkRules`, read with the `genation-workspace_document_types_list` call with `codes` ("Document types and rules", start of section 10). Each rule has `id`, `code`, `kind`, `targetField`, `message`. These are the criteria staff tick; the file becomes **Satisfied** on the CRM when every rule of the type is `met` in the latest check, or when a staff member accepts the document (section 12.5). For each rule of the type, one item `{ruleId: <id>, outcome, note?}` (no `id`: `{ruleCode: <code>, outcome, note?}`), only copying the report:
- `fact_find`, `deal_date`: `met` when the document was read and the block has the "Record in Fact Find" line for that target (target table below) with a clear value, or with the rule file's "If absent, write" value ("not on the payslip", "none (Salary sacrifice $0.00)", "not printed on the contract", "No specifically named beneficiary"…): the fact is known. `note` = the recorded value as in the line (Licence No., Document No., Account number: last 4 characters only, `…4821`). `not_checked` only when the field could not be read (the line says "Could not check", including an "If absent, write" value of "Could not check", or the value is not clearly readable), or the document lacks the page or part the rule file needs for it. Notices conditions keep their own rules below.
- `redact`: `not_met` when there is a `[TFN]` line (`note` = page with the TFN, never the number); `met` when every page was read and no TFN was found; otherwise `not_checked`.
- `notify`, `broker_note`: `not_met` when there is a "Notices" line for exactly what the rule states (`note` = `[<tag>] <evidence> → <action>`); `met` when that was checked and there is no issue; `not_checked` when it is under "Could not check" or the report does not mention it.
- `INVALID` or `UNREADABLE` block: every rule `not_checked`, except the rule for what made the file invalid, which is `not_met`. Unsure which line a rule corresponds to: `not_checked`. One item per rule, no repeats; do not add rules of another type.
- Document without a type: classify first (section 10.3), then record with `ruleResults`; if it cannot be classified, record without `ruleResults`. The tool rejects because of rules (`document_type_required`, `unknown_check_rule`, `check_rule_ambiguous`, `listed_twice`): call again once without `ruleResults`, so the check result is still recorded.

### 10.3 Classifying the document and its client

For each document with a `Conclusion:` line whose block recognised the type, before recording its result in 10.2 (so the result can include `ruleResults` per the rules of the type just set). A file not yet on the deal gets these fields in its registration (10.1). A file already on the deal: ONE `genation-workspace_deal_files_update` call with `id` = the `id` of the file on the deal and only the fields to change (no fields: do not call):
- `documentTypeCode`: only when the document has no type yet; code per the table below, only when that code is in the compact list of `genation-workspace_document_types_list` ("Document types and rules", start of section 10). Do not change an existing type.
- `subjectContactId`: the deal's client the document belongs to, in `contacts` of `deals_get`: the client whose name MATCHES; if none, the only client with the same surname and the same first name or preferred name (a missing or abbreviated middle name still counts; the report's `[Name mismatch]` line stays as is); entity: the client that is that entity. Set it when the document has no client yet, or when the current client is not that person (e.g. `mail-intake` set the email sender). Document in the name of several of the deal's clients (joint account): the first-named client. Cannot determine exactly one client: do not set, gather into the final question "which client does document <file> belong to?" (another person's document, identity.md: no such question, its action covers it).

A file already on the deal that has a client but empty `assignedContactIds`: `genation-workspace_deal_files_assign` (`id`, `contactIds` = the document's client, plus the clients named jointly) so the file shows under the right client ("Assign to"); do not replace an existing list. All registrations, `deal_files_update` and `deal_files_assign` calls of the batch go in ONE turn. This step does not rename or move files (that is only in section 12). "Type not recognised" blocks, Airbnb and types without a code: do not set a type.

| Rule | `documentTypeCode` |
|---|---|
| 1 / 2 / 3 | `proof_of_ownership` / `contract_of_sale` / `building_contract` |
| 4 / 5 / 6 / 7 / 8 | `drivers_licence` / `australian_passport` / `foreign_passport` / `medicare_card` / `visa` |
| 9 / 10 / 11 / 12 | `trust_deed` / `company_extract` / `credit_report` / `payslip` |
| 13 | `individual_tax_return`, `partnership_tax_return`, `company_tax_return`, `trust_tax_return`, `income_statement`, `notice_of_assessment`, `financial_statements` (by the type in the block heading) |
| 14 / 15 / 16 | `rental_statement` / `rental_agreement` / `rental_appraisal` (excluding Airbnb) |
| 17 / 18 | `centrelink_statement` / `child_support` |
| 19 | by the statement's purpose: `bank_statement_salary` (regular pay credits from the employer), `bank_statement_business` (account in a business name, business transactions), `bank_statement_rental` (regular rent credits), `bank_statement_expenses` (spending account, no pay or rent credits) |
| 20 / 21 / 22 / 23 | `home_loan_statement` / `liability_statement` / `study_loan_statement` / `bnpl_statement` |

**Rule 19:** the deal has exactly one open required document (10.4) of one of the four statement types, assigned to the document's client or to no one: that type. None: per the block's "Facts for cross-checking", when exactly ONE purpose is seen. Several purposes (both pay and rent credits) or unclear: do not set a type, gather into the final question "is statement <file> evidence of pay, business, rent or expenses?".

### 10.4 Completing a required document

With the tools `genation-workspace_required_documents_list` and `genation-workspace_required_documents_complete`: call `required_documents_list` (`dealId`, read all pages) once for the whole batch; the `required_documents_complete` calls go in the turn of 10.2. Completing tells staff and the client that the document has been received: the client portal stops asking for it. So complete a required document only when ALL of these hold, for the files of the deal so far (this batch and files already on the deal); otherwise leave it as it is (`requested` stays requested):
1. **Check satisfied:** every file used is `PASS` with every criterion met (`checkStatus` `satisfied`), or accepted by staff (12.5). `ACTION NEEDED`, `NOT ENOUGH INFORMATION` (`need_review`), `INVALID`, `UNREADABLE`: not yet.
2. **Fully met:** quantity and period as its `name`, `comment` and `clientNote` ask: "Latest payslips" or "2 most recent consecutive payslips" = two payslips with consecutive pay periods; "3 months' statements" = the full 3 months (`guroos_date_check`). One payslip of two, a gap, a short period: not met.
3. **The right person:** assigned to contacts (`assignedContactIds`): only their documents count (the document's client, or a joint document in their names), and each of them needs their own. Assigned to no one and the deal has several borrowers (`contacts` of `deals_get`): each borrower needs their own (Daniel's passport does not cover Emily), unless its `name`, `comment` or `clientNote` (copied from its template) says one is enough ("either applicant", "joint") or it is about the deal's property rather than a person (rules 1–3).
4. **Approved:** Ask first: part of the batch's approved changes; Full access: part of the processing asked for.

Candidates for a document with a type, not yet fulfilling any required document (no item has `fulfilledByDealFileId` = the file's `id`): required documents with status `draft`, `requested` or `rejected`, the same `documentTypeCode`, whose people (3) include the document's client; several: keep those assigned to the document's client. Exactly one, and 1–4 hold: `required_documents_complete` with `id` = the required document, `dealFileId` = the file (several files fulfil it: the one received last; name every file in the summary). One file completes at most one required document. Not all of 1–4: do not complete; say what is still missing, per person ("Latest payslips: Daniel 1 of 2, needs review; Emily none"). None: "no required document". Still several: do not complete, gather into the final question (state the items' `name`). In doubt: leave it requested.

Do not create, edit, reject or archive required documents, except the `clientNote` of a request this batch made (10.2). The tool reports `required_document_state`: write "not completed: <name> already completed".

### 10.5 After recording

Registering, classifying, completing required documents and recording are changes (approval rule, SKILL.md section 1): Full access: part of the check or processing asked for, do not ask; Ask first: covered by the ONE approval question of the batch (section 11 step 2, or the next steps after the report), never asked per file or per write; notes for the client only per 10.2. Never copy contact details into the deal (SKILL.md section 2). The user says not to record ("Check only", "No"): do not record, do not retry, the remaining files get "not recorded on the CRM: user declined". The tool reports a parameter error (`Invalid arguments: …`): fix exactly that spot per the report, call again once. Other errors (`404` document not on the deal…): write the tool's message verbatim, do not retry. Results with `warnings` (target has nowhere to record yet, client has no matching record…) are normal: only count them, do not list them.

Add one line per file under the report (a likely duplicate: `- <file> · CRM: not recorded: likely duplicate of <old file>`, 10.6): `- <file> · CRM: recorded (<conclusion>)` (just registered on the deal: add `, just registered`; type or client just set: add `, <type label> · <client name>`; required document just completed: add `, completed <required document name>`; left open (10.4): add `, <name> still open: <what is missing, per person>`; with `ruleResults`: add `, <met count>/<rule count> criteria met`; with `observationIds`: add `, Fact Find: <fields proposed, in plain words> added to Updates to review for you to accept` (10.2); with warnings: add `, <n> findings not applied`; with `requiredDocumentIds`: add `, <n> documents to request (draft)`, each note on its own line as in 10.2) or `- <file> · CRM: not recorded: <reason>`. ### 10.6 Likely duplicates

Clients often resend a document the deal already has, and a file may be on the deal twice (dropped twice: `… (2).pdf`). In both modes, before registering (10.1) or filing (section 12) ANY file in `tmp/`, whether `new` or already on the deal waiting to be filed (checked in this run or an earlier one), compare it with the same person's files of the same type on the deal (`deal_files_list`, already read: filed or in `tmp/`, `archivedAt` and `replacedByDealFileId` empty; the person = the document's client, `subjectContactId` or the one 10.3 sets) and with the other files of this run:

| Type (rule) | Same document when |
|---|---|
| Driver licence, Photo Card (4) | same Licence No. (Photo Card: card number) |
| Passport (5, 6) | same Document No. |
| Medicare card (7) | same card number (its first 9 digits; the 10th, the issue number, changes on a new card) |
| Payslip (12) | same pay period and same employer |

The values: what this run read; a file not read in this run: its latest check (`document_checks_list`, `dealFileId`, `limit` 1: the `fact_find` finding of Licence No. or Document No., and the expiry), a payslip's period and employer in its filed name; otherwise (Medicare always: its number is never recorded) read that page with `guroos_document_read` (`cloud` from its `document`). These calls go in the turn of the rule files (section 11 turn 5). Never write these numbers in the reply: "same licence number".

A match is a **likely duplicate**:
- **Newer** when its issue date or expiry (payslip: pay date; Medicare: a higher issue number or later VALID TO) is later than the old file's; otherwise a copy. A filed file is the old one. Two files not filed yet match (`new` or on the deal, in `tmp/`): process the newer (same dates: the one already on the deal; both on it: the one registered first; else the first listed); the other is the likely duplicate.
- It is checked and reported as usual (checked in an earlier run: not again, its summary line says it), with the Notes line "likely duplicate of <old file> (same <licence number | passport number | Medicare number | pay period and employer>)", but takes no part in other files' cross-checks, 10.4 or filing, and is not registered, recorded or filed: it stays in `tmp/`. Full access too: report it, leave it unfiled.
- Section 11 summary: `On the deal: not registered: likely duplicate` (already on the deal: `already there`) and `Filing: left in tmp/: likely duplicate of <old file>`.
- Next steps (SKILL.md section 7), in both modes: ONE question for all likely duplicates, each by number with the old file and why ("no. 4 tmp/IMG_2201.jpg: same licence number as 3. ID/Emily_DL.pdf, later expiry"), options "Replace the old one" (only when one is newer), "Archive the new copy", "Not a duplicate", "Leave it".

Answers (every file in ONE turn):
- **Replace the old one:** a `new` file: register it (10.1, with the classification) with `replacesDealFileId` = the old file's `id`: the old file is archived, the new one takes over its assignees and completed required documents. A file already on the deal: `deal_files_update` with its `id` and `archived` = true, then in the next turn `genation-workspace_deal_files_replace` with `id` = the old file, `documentId` = its `document.id`; use the returned file. Then 10.2, 10.4 and section 12 as for any file (Full access: file it when Satisfied; Ask first: when the answer said to file, otherwise propose it). The old file stays in its folder on OneDrive, so the new name may get ` (2)`: say so.
- **Archive the new copy:** a `new` file: register it (10.1), then in the next turn `deal_files_update` with its `id` and `archived` = true; a file already on the deal: that call only. It stays in `tmp/` on OneDrive; staff may delete it there. Line: `- <file> · archived as a duplicate of <old file>`.
- **Not a duplicate:** process it as any new file (10.1–10.4, section 12). **Leave it:** nothing; it is flagged again next time.
